## Four different things that must not be confused

| Concept | Meaning | Where it shows |
|---|---|---|
| **Investigated** | The relevant source, behaviour or requirement was examined (read, traced, run, screened). Examination alone, and a defect found by examining, establish nothing about whether the requirement is satisfied | Stage `I`; status In Progress when nothing more is established |
| **Remediated** | An approved implementation change was completed (so far only Phase 0: layout, tooling, runner, test repairs, file removal, history purge; no tracker behaviour has been changed) | Stage `+R` |
| **Verified** | Evidence establishes that the specific requirement is satisfied over its whole scope, with the evidence named and any limit recorded. A file read, a function traced, a passing test that asserts something narrower, a fix made, or no defect found are not verification | Status Verified (stage `+V`); Partially Verified is stage `+partial V` |
| **Independently verified after remediation** | A separate verification effort, not made by the session that implemented the change, confirms the fix | None exists. Phase 0 self-checks (runner self-test, injected failures, V-1 to V-10) were made by the implementing session |

## How to read this matrix

**Statuses** (only these seven):

| Status | Meaning here |
|---|---|
| Not Started | No examination of this requirement has been done |
| In Progress | The requirement was investigated, or is an ongoing conduct obligation, but no part of it is established by sufficient evidence of the requirement itself. Rows with no evidence at all are counted as not yet investigated (see the counts) |
| Partially Verified | Real evidence (test, exhaustive check on part of the scope, independent source or recorded determination) establishes part of the requirement; the gaps are in Remaining work and Limitations. An open defect on the requirement keeps it here only if part of the requirement is established |
| Verified | The specific requirement is established by sufficient evidence over its whole scope, with named evidence and no material gap. Rows whose evidence is a file read or function trace, a sampled test narrower than the requirement, a result limited to the local stand-in, or a check made only at an earlier session are not Verified |
| Blocked | Cannot proceed until a named external condition is met (for example the real provider and the Q5 test artifact) |
| Deferred | Postponed by an explicit owner decision |
| Not Applicable | The requirement does not apply (none so far) |

**Rules applied.** Verification is evidence-based and does not follow from implementation: a fixed defect needs the corrected behaviour tested against the relevant scenarios before the requirement can rise in status. Completing Phase 0 does not establish that the architecture, game-data, accessibility, security or release audits are complete. A passing test counts only for what it asserts; scripts that print no verdict are UNCHECKED in the runner and are never treated as passes. A status can fall as well as rise. Where a row once read Verified and was lowered, the reason is in its Limitations column ("Governance review: status changed from ...").

**Columns.** ID, original specification section and requirement, audit category, status, stage (I investigated, R remediated, V verified, partial V partially verified), relevant files or functionality, sessions or phases that examined it (S1 to S5 are the original investigation sessions, P0 is Session 6 Phase 0), basis (`INV` original investigation, `INV+P0` investigation work re-executed or whose subject was changed by Phase 0), supporting evidence, related finding IDs, remaining work, known limitations, next required action. Test-case ids such as S1a, S17, N2, R, B1-B8, P1-P5, H1 and G1 belong to the audit scripts and are written with the script name where they could be mistaken for session labels (S1 to S5).

## Maintenance rules for this document

1. Update the affected rows at the end of every audit or remediation session, before the session report. Change a status only with new evidence, and add that evidence (script, log path, source) to the row.
2. Never raise a status because an implementation phase completed. After a fix, run the relevant scenarios, record the run as evidence, and only then change the status; say whether the verification was independent of the implementing session. Only a separate verification effort counts as independent verification after remediation.
3. Never delete a row or renumber IDs. A superseded row keeps its ID with a dated note.
4. Statuses may fall when a finding or regression shows an earlier conclusion was too strong; keep the earlier status in the note.
5. The final assessment may be written only when the section 13G conditions are met; rows still Not Started, In Progress or Blocked must then be listed in the Audit Coverage Report (specification 12H).
